このサイトの作り方 — ガードレールを土台にした技術ノートサイト

セキュリティ 2026-06-28

このサイト（tech-memo）は、技術的に学んだことを書き留めて公開するための 小さな静的サイトです。記念すべき最初のノートとして、このサイト自体を 「どう作ったか」、とくに誤って機密情報を公開しないための仕組み （ガードレール）をどう組んだかを解説します。

これからリポジトリを公開してみたい初心者エンジニアの方にも分かるよう、 途中で必要な周辺知識を補足しながら進めます。

そもそも何を作ったのか

作ったのは静的サイトです。静的サイトとは、サーバ側で プログラムを動かさず、あらかじめ用意した HTML / CSS ファイルを そのまま配信するだけのサイトのこと。データベースもサーバ言語も不要で、 構成がシンプルなため、個人の技術メモ置き場には十分です。

構成はおおよそ次のとおりです。

.
├── index.html              # トップページ（ノート一覧）
├── styles/site.css         # 共通スタイル
├── notes/
│   ├── template/index.html # 新規ノートのひな形
│   ├── _drafts/            # 未完成の下書き置き場
│   └── <公開日-スラッグ>/    # 公開済みノート（この記事もここ）
├── AGENTS.md               # 作業ルール（人にもAIにも適用）
└── PUBLISHING_CHECKLIST.md # 公開前チェックリスト

設計の核心：「ガードレールを先に作る」

このプロジェクトで最初に決めたのは、記事を書き始める前に、 まずガードレール（安全装置）を作るという順番でした。

ガードレール＝「うっかり機密情報を公開してしまう」「未完成の記事が 公開される」といった事故を、人の注意力に頼らず仕組みで防ぐ仕掛け。

なぜ順番が大事かというと、Git の履歴は消しにくいからです。 ここでいう「シークレット（secret）」とは、パスワード・API キー・秘密鍵など、 外部に漏れてはいけない文字列のこと。これらをうっかりコミットすると、 たとえ次のコミットで消しても過去の履歴には残り続けます。 公開リポジトリなら、その一瞬で世界中から見られた可能性があります。 だからこそ「最初の1コミット目から」防御が効いている状態にしたい—— これがガードレール先行の理由です。

多層防御：5つの層で守る

一つの仕組みに頼ると、それが破られたら終わりです。そこで、性質の違う 防御を重ねて配置しました（多層防御）。

層1：.gitignore — そもそも追跡しない

.gitignore は「Git に追跡させないファイル」を指定する 設定ファイルです。.env（環境変数ファイル）や *.key（鍵ファイル）などをここに書いておけば、 そもそも git add の対象から外れ、事故の母数を減らせます。

層2：pre-commit + gitleaks — コミット前の自動チェック

次は手元（ローカル）での防御です。Git には「フック（hook）」という、 特定のタイミングで自動的にスクリプトを走らせる仕組みがあります。 その一つ pre-commit フックは、git commit の直前に実行されます。

この仕組みを手軽に扱うツールが pre-commit （同名のフレームワーク）で、設定ファイルにチェック項目を並べるだけで コミット前検査を自動化できます。そこに、シークレット検出ツール gitleaks を組み込みました。 

# .pre-commit-config.yaml（抜粋）
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.30.1
    hooks:
      - id: gitleaks            # 鍵やトークンらしき文字列を検出
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v6.0.0
    hooks:
      - id: detect-private-key  # 秘密鍵の混入を検出
      - id: check-added-large-files
        args: ["--maxkb=1024"]  # 大きすぎるファイルを防ぐ

導入は pip install pre-commit のあと pre-commit install を一度実行するだけ。以降は コミットのたびに自動で検査が走り、シークレットらしき文字列があれば コミットが中断されます。これが一次防御です。

層3：GitHub の Secret scanning / Push protection — サーバ側の網

ローカルの防御は、各自が pre-commit install を 忘れると効きません。そこで GitHub 側にも網を張ります。 Secret scanning は、リポジトリ内に既知の形式の シークレットがないかを GitHub が走査する機能。 Push protection は、シークレットを含む push を その場でブロックする機能です。これらは管理画面（Settings）で 有効化します。

層4：CI — PR のたびに自動検査する

CI（継続的インテグレーション）とは、コードの変更を 取り込むたびに、自動でテストや検査を走らせる仕組みのこと。GitHub では GitHub Actions を使い、リポジトリ内の YAML ファイルに 手順を書くと実現できます。

ここでは guardrails という名前のジョブを作り、Pull Request （後述）のたびに2つの検査を回しています。

  • gitleaks：層2と同じシークレット検出を、今度は サーバ上で。手元で検査を忘れても、ここで止まります。
  • lychee：HTML 内のリンク切れ（存在しない URL への リンク）を検出するツール。公開物の品質を守ります。
# .github/workflows/pre-publish-check.yml（抜粋）
on:
  pull_request:
    branches: ["main"]
jobs:
  guardrails:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@... # SHA固定（後述）
        with:
          fetch-depth: 0
      - uses: gitleaks/gitleaks-action@...
      - uses: lycheeverse/lychee-action@...
        with:
          args: --no-progress './**/*.html'

層5：ブランチ保護 — main を直接触らせない

最後の層は運用ルールです。まず用語を整理します。

  • ブランチ：変更を枝分かれさせて作業する単位。 公開される本番の枝が main。
  • Pull Request（PR）：ある枝の変更を main に取り込む前に、差分を見せて確認・検査するための仕組み。

GitHub のブランチ保護（ルールセット）で、 main への直接の書き込みを禁止し、「PR を経由すること」 「guardrails チェックに通ること」を必須にしました。 こうすると、層4の検査を必ず通らないと公開できません。

一人で運用していても、PR を挟むこと自体が「自分のコミットをもう一度 見直す冷却期間」になり、誤公開対策として有効に働きます。

もう一歩の堅牢化：アクションの SHA 固定と Dependabot

層4で使った actions/checkout などは、他人が作って公開した 部品（GitHub Action）です。便利な反面、その部品が乗っ取られて悪意ある コードに差し替えられると、こちらの CI も汚染されます。これを サプライチェーン攻撃と呼びます。

対策として、各アクションを @v4 のような「動くタグ」では なく、特定のコミット SHA（中身が変わらない固定の識別子） で参照するようにしました。 

uses: actions/checkout@34e114876b0b11c390a56381ad16ebd13914f8d5 # v4.3.1

ただし固定したままだと、セキュリティ修正にも追従できません。そこで Dependabot（依存関係の更新を自動で提案してくれる GitHub の機能）を有効にし、固定 SHA と版数コメントを定期的に 更新してもらう運用にしています。「固定」と「鮮度」を両立させる構えです。

日々の執筆〜公開のワークフロー

記事を1本公開するまでの流れはこうです。

  1. ひな形 notes/template/index.html を元に、下書きを notes/_drafts/<slug>.html に作る。 _drafts/ はトップからリンクしないので未公開のまま。
  2. 書き終えたら PUBLISHING_CHECKLIST.md（公開前 チェックリスト）で、個人情報・社内情報が無いか等を確認する。
  3. 記事を notes/<公開日-スラッグ>/index.html へ移動し、 トップページのノート一覧にリンクを追加する。
  4. PR を出し、guardrails チェックが緑になったらマージ＝公開。

ちなみに、下書きも公開記事もテンプレートも「ルートから2階層下」に そろえてあるので、CSS への相対パス（../../styles/site.css）は 移動しても変わりません。地味ですが、こうした小さな一貫性が事故を減らします。

まとめ

この記事では、技術ノートサイトを「ガードレールから先に」作った流れを 紹介しました。ポイントは、防御を人の注意力ではなく仕組みに 肩代わりさせること、そして性質の違う防御を重ねる ことです。最初に土台を作っておけば、安心して中身（記事）の執筆に 集中できます。同じように個人サイトを始めたい方の参考になれば幸いです。
