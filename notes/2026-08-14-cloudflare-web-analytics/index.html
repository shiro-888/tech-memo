Cookieを使わないアクセス解析、Cloudflare Web Analyticsを静的サイトに入れる

ツール 2026-08-14

GitHub Pages でサイトを公開すると、そのうち「で、これ誰か読んでるの？」が気になってくる。 ところが GitHub Pages 自体にはアクセス解析の機能がない。HTML を置けば配信してくれるだけで、 何ページ読まれたかは教えてくれない。

リポジトリの Insights にある Traffic を見たことがある人もいると思う。あれは近いようで別物で、 直近14日ぶんしか残らず、閲覧できるのはリポジトリへの push 権限を持つ人だけ。 しかも数えているのは主にリポジトリページへの訪問とクローンで、公開サイト側のページ閲覧を そのまま表しているわけではない。長期の傾向を追う用途には向かない。

そこで候補に挙がるのが Cloudflare Web Analytics。Cookie を使わず、DNS を Cloudflare に 向け直す必要もなく、無料で使える。このノートでは仕組みと導入手順、それから 「何が測れないか」を整理する。

何をするサービスなのか

ひとことで言うと、ページに JavaScript を1行貼ると閲覧数と表示速度を集計してくれるサービス。 Cloudflare の公式ドキュメントは「訪問者の個人データを収集しない」と明記していて、 Cookie も localStorage も使わない設計になっている。

Cloudflare のサービスというと DNS を移管して全トラフィックを通す構成を想像しがちだが、 Web Analytics はそれを前提にしていない。ドキュメントには、むしろ Cloudflare のプロキシを 使っていない利用者向けに設計されているという趣旨の記述がある。 GitHub Pages のように配信そのものは他社に任せたままでも、計測だけ借りられる。

ビーコンが動く流れ

計測を担うのは beacon.min.js という小さなスクリプト。ブラウザが記事ページを 読み込むと、このスクリプトが Performance API（ブラウザが持つ表示性能の計測 API）から 読み込み時間などを取り出し、Cloudflare 側へ送る。手動で貼った場合の送信先は cloudflareinsights.com/cdn-cgi/rum になる。

ここで押さえておきたいのは、計測がブラウザ側の JavaScript で完結している点。 サーバーのアクセスログを解析する方式ではないので、JavaScript が動かない環境の閲覧は そもそも数に入らない。後述する広告ブロッカーの話もここから来ている。

Cookieなしでどうやって訪問数を数えるのか

一番おもしろいのがこの部分だと思う。普通のアクセス解析は Cookie に ID を書き込んで 「同じ人が戻ってきた」を判定する。Cloudflare はそれをやらない。 発表時のブログでも、Cookie や localStorage といったクライアント側の状態を使わない、 IP アドレスや User-Agent で追跡するのはもっと侵襲的だ、という立場を取っている。

では訪問数（visits）はどう出しているのか。ドキュメントの定義はこうなっている。

A page view that originated from a different website or direct link. （Cloudflare Docs, High-level metrics）

つまり HTTP リファラ（どのページから来たかを示すヘッダ）が自分のホスト名と一致しない ページ閲覧を1訪問として数えている。サイト内のリンクをたどった2ページ目以降は リファラが自ホストになるので、閲覧数だけ増えて訪問数は増えない。

この割り切りの代償として、いわゆるユニークユーザー数は出ない。 同じ人が3日連続で検索から来れば3訪問。逆に言えば「誰が」を保存していないからこそ Cookie 同意バナーの話にならずに済んでいる、という設計上のトレードオフになっている。

なお閲覧数（page views）の定義は「content-type が HTML の成功した HTTP レスポンス」。 画像や CSS の取得はカウントされない。

GitHub Pagesへの入れ方

手順自体は拍子抜けするほど短い。Cloudflare ダッシュボードの Web Analytics を開き、 Add a site から計測したいホスト名（ユーザー名.github.io や独自ドメイン）を 登録する。すると Manage site にスニペットが出てくるので、それを HTML の </body> の直前に貼る。形はこうなる。 

<!-- Cloudflare Web Analytics -->
<script defer src="https://static.cloudflareinsights.com/beacon.min.js"
        data-cf-beacon='{"token": "YOUR_TOKEN"}'></script>
<!-- End Cloudflare Web Analytics -->

YOUR_TOKEN の部分にはダッシュボードが発行した文字列が入る。 これは公開ページの HTML に載る前提の値なので秘密鍵の類ではないものの、 別サイトのトークンを流用すると集計先が混ざるので、サイトごとに発行したものを使う。

注意したいのは、貼る作業がページ単位だということ。このサイトのようにビルドツールを 使わず素の HTML を並べている構成だと、記事を1本増やすたびにスニペットの貼り忘れが起きうる。 テンプレート（notes/template/index.html）側に先に入れておくのが現実的だと思う。 Jekyll を使っているなら _layouts や _includes の共通レイアウトに 1回書けば済む。

ページ遷移で HTML を読み直さない SPA には別の入れ方が用意されていて、 data-cf-beacon に spa の設定を渡すとルート変更も拾ってくれる。 素の静的サイトなら気にしなくていい。

ダッシュボードで見られるもの

訪問数と閲覧数に加えて、ページ別・リファラ別・国別・ブラウザ別といった内訳が並ぶ。 アクセス解析としては標準的な顔ぶれで、目新しさはない。

個人的におまけとして嬉しいのは表示速度のほう。Core Web Vitals として LCP（主要コンテンツが表示されるまでの時間）、INP（クリックなどの操作に反応する速さ）、 CLS（読み込み中にレイアウトがずれる度合い）が、実際の訪問者のブラウザで計測した値として Good / Needs Improvement / Poor の判定つきで出る。Lighthouse が自分の手元1台で測るのに対し、 こちらは本当の閲覧環境の分布が見える。

期待しすぎないほうがいいところ

便利なぶん、数字の性質は理解して使いたい。導入前に知っておきたい点を挙げる。

  • 広告ブロッカーに止められる。FAQ 自身が adblockplus、Brave、DuckDuckGo の 拡張機能でビーコンがブロックされると認めている。技術系の記事は読者にブロッカー利用者が 多いので、実際の閲覧より少なめの数字が出ると考えておく。
  • 古いデータは薄まる。取り込み時点ではサンプリングしないが、7日を過ぎたぶんは 約10%に集計され、参照できるのは過去6か月ぶんとされている。 先月の数字と今週の数字は同じ解像度ではない。
  • 無料プランではルールが0件。プロキシ配下のサイトで計測対象を絞り込むルール機能は Pro 以上の機能で、Free は使えない。またプロキシを通していないサイトの登録は10件まで。

ブロッカーの影響を受けない計測が欲しいなら、リクエストそのものを数えるサーバーサイドの 方法（Cloudflare のエッジ解析や、配信元のアクセスログ）を選ぶことになる。 ただし GitHub Pages はアクセスログを利用者に見せてくれないので、その道は最初から塞がっている。

他の選択肢と比べてどうか

同じ枠には GA4、Plausible、GoatCounter あたりが並ぶ。GA4 は取れる情報が桁違いに多い代わり、 Cookie を使うのでプライバシーポリシーや同意まわりの検討が付いてくるし、 個人の技術ノートに対しては明らかに過剰。Plausible や GoatCounter は プライバシー重視の軽量解析という点で性格が近く、GoatCounter は個人サイト向けの無料枠がある。

Cloudflare Web Analytics を選ぶ理由があるとすれば、無料で、貼るのが1行で、 同意バナーを考えずに済んで、ついでに実ユーザーの Core Web Vitals まで見える、という 手間に対する見返りの良さだと思う。逆に、読者ひとりひとりの回遊を追いたいとか、 ブロッカー込みで正確な実数が欲しいといった要求には応えられない。 「だいたい何人くらいに読まれていて、どの記事が伸びているか」を知りたいだけなら十分で、 個人の技術ノートの用途はたいていそこに収まるはず。
