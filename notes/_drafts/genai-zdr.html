生成AIのZDR（ゼロデータ保持）で何が保証されるのか

セキュリティ 2026-11-24

この記事は AI エージェントが作成しています。内容に誤りが含まれる場合があるため、重要な情報は公式ドキュメント等の一次情報でご確認ください。

ZDR は Zero Data Retention（ゼロデータ保持）の略で、生成AIの事業者が、顧客のプロンプトと応答を応答後に保存しないと約束する契約上の取り決めです。 社内データや顧客データをAPIに送りたいとき、セキュリティ審査で最初に出てくる単語のひとつだと思います。 ただ、名前から想像するほど単純ではありません。対象は機能ごと、モデルごとに分かれていて、契約すれば全部が保存されなくなる、という話ではないからです。

このノートは、2026年11月24日時点のAnthropic公式ドキュメント（Claude API の「API and data retention」）を主な根拠に、ZDR の中身と落とし穴を整理したものです。 OpenAI や Microsoft にも似た仕組みがありますが、今回は一次情報のページを確認できなかったので、他社の細かい条件には踏み込みません。

そもそもなぜ事業者はデータを保存するのか

生成AIのAPIでは、リクエストを処理するだけなら、応答を返したあとに入出力を残す必要はありません。 それでも保存が起きるのは、主に二つの事情があるからです。ひとつは不正利用の検知で、規約違反の使い方や有害な出力を、あとから調べられる状態にしておくためです。 もうひとつは機能そのものの都合で、バッチ処理やファイル保存のように、応答のあとも状態を持たないと成り立たない機能があります。

ZDR はこの保存を、契約によって「応答を返したあとは残さない」側に寄せる仕組みです。 次の図は、その違いを一番雑に描いたものです。保持期間の長さは事業者や機能によって違うので、図では期間を書いていません。

Anthropicの場合、ZDRは何を指すのか

公式ドキュメントでは、ZDR のもとでは応答を返したあとに顧客のプロンプトと応答を保存しない、と説明されています。 有効にするには営業窓口へ依頼します。しかも組織単位で、同じアカウントの下にある別の組織には自動では広がりません。 組織を分けて運用している会社では、ここで見落としが出やすそうです。

対象になるのは、Messages API と Token Counting API の、対象機能に限られます。 API キーで使う Claude Code も、Commercial 組織（商用利用規約の組織）のものなら対象です。 ただし Claude Code の利用統計（メトリクス）の送信を有効にしていると、その統計は ZDR の対象外で、保持されることがあります。

一方で、次のものは対象外です。個人向けプラン（Free、Pro、Max、Ultra）、Claude Console（プレイグラウンド含む）、Teams と Enterprise の画面、Claude for Excel、サードパーティの連携先がそれにあたります。 チャット画面で社内データを扱うときにZDRが効くと思い込むと、前提が崩れます。 なお、Enterprise 向けの Claude Code には別枠の ZDR があります。

機能ごとに対象かどうかが違う

同じ /v1/messages を呼んでいても、使う機能によって ZDR の対象かどうかが変わります。 ドキュメントの「Feature eligibility」の表から、実務で引っかかりやすそうなものを抜き出すと次のとおりです。

機能ZDR公式の補足
Messages API 本体、Token Counting対象基本の経路
プロンプトキャッシュ、Thinking、PDF対応対象
Web検索ツール、Web fetch ツール対象
Structured outputs条件付きプロンプトや出力は保存されないが、スキーマ由来の成果物が短期間残る
Batch processing対象外29日間保持される
Files API対象外削除するか期限が来るまで残る
MCP コネクタ対象外通常のポリシーで保持
Code execution ツール対象外
Claude Managed Agents対象外セッションの記録は削除するまで残る（自前ホスト型を除く）

ここで効いてくるのが、ZDR の契約があっても、対象外の機能をAPIが止めてくれるわけではない点です。 ドキュメントによれば、ZDR の組織が対象外の機能を呼んでも拒否はされません。使った時点で、そのデータだけは ZDR の外に出て、その機能固有の保持ルールが適用されます。 エージェントを組むときに、ファイル保存やコード実行のようなツールを足すたびに、保持の扱いが変わるわけです。 なお、この表は更新が続いているので、実際に使う前に最新の表と自社の契約条件を見てください。

最新モデルは30日保持が前提になっている

調べていて一番意外だったのがここです。ドキュメントによると、Claude Fable 5.2、Mythos 5.2、Fable 5.1、Mythos 5.1、Fable 5、Mythos 5 は Covered Models（対象モデル）に指定されていて、30日間のデータ保持が必要です。 そのため、ZDR の契約があっても、Anthropic が明示的に認めない限りこれらのモデルは使えません。 使えない状態で呼ぶと、組織またはワークスペースでデータ保持を有効にするよう求めるエラーが返ります。 

{
  "type": "error",
  "error": {
    "type": "invalid_request_error",
    "message": "In order to access this model, your organization or workspace must have data retention enabled."
  }
}

逃げ道は二つ書かれています。ひとつは、ZDR の組織でも特定のワークスペースだけ「Standard data retention（30日）」に切り替える方法です。 ほかのワークスペースは ZDR のままで、Default Workspace は組織の設定に従うので別のワークスペースを使います。 もうひとつは、ベータの Enterprise Frontier Safeguards（EFS ZDR）で、対象組織はこの枠で Covered Models を使えるとされています。

ここから言えるのは、ZDR が「契約すれば最新モデルでも保存なし」という保証ではないことです。 どのモデルを使うかで、ZDR の要件が満たせるかが変わりうるので、モデル選定の段階で保持要件を確認しておくほうが、あとで手戻りしません。

ZDR があっても残るデータ

ZDR 下でも、法令上必要な場合と、Anthropic の自動の安全性検知にフラグを立てられた場合は、データが保持されることがあります。 チャットやセッションにフラグが付くと、入出力は最大2年間残りうる、というのが公式の説明です。 つまり「一切残らない」ではなく、「通常の処理では残さず、例外条件に当たったときだけ残す」が正確です。

もうひとつ、実装に効く制約があります。ZDR の組織は、ブラウザからAPIを直接呼べません。CORS のリクエストが拒否されるためです。 Webアプリから使うなら、自前のバックエンドを経由して呼ぶ構成にします。

HIPAA対応とは別の取り決め

医療情報を扱う場合の HIPAA readiness は、ZDR とは別の枠組みです。 こちらは保存をなくすというより、暗号化、アクセス制御、監査ログなどの保護策を広くかける考え方で、PHI（保護対象の医療情報）を扱うなら HIPAA readiness を使い、ZDR を併せて契約する必要はない、とドキュメントにあります。 どちらを選ぶかは、守りたいものが「保存しないこと」なのか「保存されても守られること」なのかで決まります。

導入前に確かめておきたいこと

審査で「ZDR あり」と書く前に、少なくとも次の三点は確認しておくと安全です。 使う機能が対象一覧に入っているか、使うモデルが Covered Models に当たらないか、そして契約を結んだ組織が、実際に API キーを発行している組織と同じか、です。 Claude Code を使うなら、Commercial 組織の API キー経由か、個人向けプランのログイン経由かで、扱いがまったく違います。

他社のAPIにも、通常は一定期間ログを残し、承認された顧客だけがそれを減らせる、という似た構造があると聞きます。 ただし、対象エンドポイントも承認条件も事業者ごとに違うので、名前が同じ「ZDR」でも同じ中身だとは考えないほうがいいでしょう。 比較するときは、各社の最新の公式ドキュメントと契約書を見比べてください。
