生成AI活用レベルはどう測る？ 内製開発の事業会社が押さえたい代表的な指標

AI 2026-07-22

現場に GitHub Copilot やチャット型の生成AIを配ってしばらく経つと、たいてい経営層から同じ質問が飛んでくる。「で、結局どれくらい効果が出てるの？」。答えに詰まった経験のある人は多いと思う。ライセンス費用は毎月しっかり出ていくのに、成果のほうは肌感覚でしか語れない。この居心地の悪さが、活用レベルをきちんと測りたいという話につながっていく。

とくに外注中心から内製開発へ舵を切った事業会社では、この問いが重くのしかかる。「内製化して開発を自分たちの手に取り戻す」という判断の延長で生成AIを入れているぶん、その投資が本当に前に進んでいるのかを説明する責任が、社内に生まれるからだ。ここでは、生成AIの活用レベルを測るときによく使われる代表的な指標を、いくつかの視点に分けて整理する。ツール名や流行りの数字を並べるより、どういう考え方で指標を選ぶかのほうが長く役に立つはずなので、そこを軸にしたい。

まず「先行指標」と「遅行指標」に分けて考える

指標を語る前に、ひとつだけ土台になる区別を置いておきたい。先行指標（リーディング指標。原因に近い、早く動く数字）と遅行指標（ラギング指標。結果に近い、遅れて動く数字）の違いだ。すごく雑に言うと、先行指標は「アクセルを踏んでいるか」、遅行指標は「実際にどれだけ進んだか」を表す。

生成AIの活用でいえば、ツールの導入率や提案の受諾率は先行指標にあたる。使われているかどうかがすぐ数字に出る。一方で、開発チームがどれだけ速く安全にリリースできるようになったか、さらにその先の事業成果は遅行指標で、効果が数字に表れるまで時間がかかる。両方をつなげて眺めるのがコツで、片方だけを見ると判断を誤りやすい。

利用の広さを測る（先行指標）

いちばん手前にあるのが「そもそも使われているか」だ。ここで代表的なのが、導入率（付与したライセンスのうち実際に使っている人の割合）、アクティブ利用率（日次・週次で触っている人の数）、そして提案の受諾率（AIが出した補完のうち採用された割合）の3つになる。GitHub Copilot なら、管理者向けの利用メトリクス API から、アクティブユーザー数や受諾率、生成された行数といった値を取り出せる。

気をつけたいのは、受諾率をゴールにしてしまう危うさだ。受諾率は「提案がどれだけ的を射ているか」の目安にはなるが、高ければ高いほど良いという単純な数字ではない。中身をよく見ずにタブキーで受け入れているだけかもしれないし、言語やコードベースによって水準は大きく変わる。一般には3割前後が目安と語られることが多いものの、この数字を追い求めること自体が目的化すると、いわゆる虚栄の指標（見栄えは良いが意思決定に使えない数字）になってしまう。利用の広さは「入り口が開いているか」の確認にとどめ、成果の話は次の遅行指標に預けるのが健全だと思う。

開発成果を測る（DORA Four Keys）

開発チームのパフォーマンスを測る定番が、DORA（DevOps Research and Assessment）の Four Keys と呼ばれる4指標だ。もともとは生成AIとは関係なく、ソフトウェアデリバリーの実力を測る枠組みとして広く使われてきた。生成AIの効果を「開発の実際の成果」まで落として見たいときに、この4つが物差しになる。

指標 何を見るか 速さ / 安定のどちら
デプロイ頻度 本番へどれだけ頻繁にリリースできているか 速さ
変更のリードタイム コードを書いてから本番に届くまでの時間 速さ
変更失敗率 リリースのうち障害や切り戻しになった割合 安定
サービス復旧時間 障害が起きてから復旧するまでの時間 安定

面白いのは、生成AIを入れれば Four Keys が自動で良くなるとは限らない点だ。DORA が毎年出している State of DevOps レポートの近年版では、生成AIの利用が個人の生産性や仕事の満足度を押し上げる一方で、デリバリーの安定性やスループットにはむしろマイナスに働きうる、という一見ちぐはぐな結果が報告されている。理由のひとつとして指摘されているのが、AIで一度に書けてしまうぶん変更の粒が大きくなり、大きな変更ほどリスクが高いという昔からの経験則がそのまま効いてくること。個人の手元が速くなっても、チームのリリースが速く安全になるとは限らない。ここが先行指標と遅行指標を分けて見るべき理由そのものだ。

開発者体験を多面で測る（SPACE）

Four Keys がデリバリーの結果を見るのに対し、開発者の体験まで含めて多面的に測ろうというのが SPACE フレームワークだ。DORA の研究者でもある Nicole Forsgren らが2021年に提唱したもので、生産性を単一の数字で語ってはいけない、という問題意識から生まれている。頭文字が5つの観点を表す。

  • Satisfaction（満足度・幸福感）… 開発者が仕事や道具にどう感じているか
  • Performance（成果）… アウトプットが生んだ結果や品質
  • Activity（活動量）… コミットやレビューなど数えられる作業量
  • Communication・Efficiency（協働と効率）… 円滑に連携し、無駄な待ちなく流れているか

SPACE のいちばんの教えは「1つの次元だけで測るな」に尽きる。たとえば活動量（Activity）だけを追うと、コミット数を稼ぐ動きを誘発してしまう。生成AIの評価でも同じで、受諾率という活動量に、満足度アンケートや実際のデリバリー成果を組み合わせて初めて、バランスの取れた絵が見えてくる。全部の次元を測る必要はなく、自社の関心に合わせて2〜3個を選ぶ使い方で十分だとされている。

組織の成熟度という視点

ここまでは数字の指標だったが、もうひとつ「組織がどれだけ生成AIを使いこなす体になっているか」という成熟度の視点がある。個人的にはここがいちばん効くと思っている。DORA の近年のレポートでも、生成AIから成果を引き出せているチームには、明確な社内方針、質の高い内部データへのアクセス、小さく速いデリバリーの習慣といった組織側の土台が共通している、という分析が示されている。

裏を返すと、ツールを配って受諾率を眺めているだけでは成熟度は上がらない。内製開発の事業会社にとってはここが正念場で、AIに読ませられる形でドキュメントやコードが整理されているか、レビューやテストの仕組みが大きな変更を受け止められるか、といった地味な足腰づくりが、そのまま生成AIの効き目を左右する。数値目標を先に立てるより、この土台を一段ずつ上げていく発想のほうが、遠回りに見えて近い。

じゃあ何から始めるか

指標を並べると全部測りたくなるが、最初から網羅しようとすると、たいてい計測そのものに疲れて続かない。現実的なのは、遅行指標を1つ（たとえば変更のリードタイム）決めて、それを説明できる先行指標を2〜3個（導入率と受諾率、開発者満足度あたり）ひも付ける、くらいの小さな出発点だ。そこから3か月ほど眺めて、先行指標が動いたときに遅行指標がついてきているかを確かめる。

逆にハマりやすいのが、受諾率だけを追う、あるいは生成された行数をそのまま成果とみなす、といった単一指標への偏りだ。行数は「たくさん書けた」ことは示しても「良いものを届けた」ことは示さない。正直に言うと、私自身もはじめは分かりやすい数字に飛びつきがちだった。指標は現場を映す鏡であって、鏡そのものを磨くのが目的ではない。そう思い出せるかどうかが、測定を続けられるかの分かれ目になる気がしている。
