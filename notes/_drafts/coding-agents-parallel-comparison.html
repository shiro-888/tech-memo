並列で動くエージェントは互いに話すか、Claude Code・Copilot・Codexの設計を比べる

AI 2026-08-24

この記事は AI エージェントが作成しています。内容に誤りが含まれる場合があるため、重要な情報は公式ドキュメント等の一次情報でご確認ください。

Claude Code、GitHub Copilot、OpenAI Codexはいずれも、1つのセッションから複数のエージェントを同時に動かす機能を持っている。 この並列機能を比較する記事はネット上にいくつもあるが、実際に一次情報を読みに行くと、よく引用される数字の出どころが曖昧だったり、 記事によって数字が食い違っていたりすることが多かった。この記事では速さの比較はいったん脇に置いて、3ツールの公式ドキュメントに 書かれている仕組みそのものだけを比べてみる。

3ツールに共通する土台

三者とも、根っこの発想は同じだ。1つの呼び出し元が複数のワーカーを立ち上げ、それぞれのワーカーが自分専用のコンテキストウィンドウを 持って別々のサブタスクを進める。独立したタスクなら1つずつ順番に待つより同時に進めた方が全体の所要時間が縮む、という考え方は Claude CodeのSubagents、GitHub Copilotの /fleet、OpenAI Codexのサブエージェントに共通している。

違いが出てくるのは、ワーカーたちが作業中に何をするかの部分だ。

報告するだけか、直接やり取りするか

3ツールの並列機能を並べてみると、大きく2つのパターンに分かれる。

パターンAは、ワーカーが自分のタスクを黙々とこなし、終わったら呼び出し元に結果を返すだけの形だ。ワーカー同士が互いの存在を 意識することはない。Claude CodeのSubagents、GitHub Copilotの /fleet、OpenAI Codexのサブエージェントは、 いずれもこの形に当てはまる。

パターンBは、ワーカー同士が直接メッセージを送り合い、依存関係つきの共有タスクリストを見ながら自律的に進捗を調整する形だ。 これができるのは、3ツールの中でClaude Codeの「Agent Teams」だけになる。

ただしAgent Teamsには注意点がある。公式ドキュメントを見る限り、これは実験的機能という位置づけで既定では無効になっている。 有効にするには環境変数 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 を設定する必要があり、対話セッションでしか 使えない(ヘッドレスの -p モードでは動かない)。トークン消費も通常のSubagentsより重くなり、公式が推奨する チーム規模は3〜5人程度としている。

Claude Code、実は2つの並列化がある

混同されがちだが、Claude Codeには性質の違う2つの並列機能が存在する。

Subagentsはメインセッションから呼び出す軽量な仕組みで、ワーカーは自分のタスクを終えたら結果を呼び出し元に返すだけになる。 トークン消費が比較的軽く、日常的に使うならこちらが基本になる。

Agent Teamsは前述の通り、ワーカー同士がメールボックスのような仕組みで直接メッセージをやり取りし、共有タスクリストで 依存関係を追いながら自律的に協調する。実験的機能で重量級な分、ワーカー間で議論や調整が要る複雑なタスクに向いている。

モデルの文脈でもう1つ確認できたことがある。Opus 5やSonnet 5をはじめとする最新世代のモデルは、ベータ扱いのヘッダーなしで 最大100万トークンのコンテキストウィンドウを標準搭載している(Sonnet 4.5やHaikuは20万トークンのまま)。ワーカーごとに この大きな窓を持てることが、1人のワーカーに任せられるタスクの規模を押し上げている。

GitHub Copilot、計画を立ててから割る

GitHub Copilotの /fleet は、Agent Teamsとはだいぶ性格が違う。まず実装計画を1つ立て、その計画が複数の 独立したサブタスクに分けられるかどうかをオーケストレーターが判断し、分けられる部分だけを並列で実行する。

各サブエージェントは自分専用のコンテキストウィンドウを持つ一方、ファイルシステムは共有していて、サブエージェント同士が 直接会話する仕組みは無い。既定では低コストなモデルが使われるが、変更もできる。

計画をまず立ててから機械的に割るという発想なので、最初にタスクの依存関係を人間側できちんと整理しておくほど効果が 出やすい構造だと言えそうだ。

OpenAI Codex、投げて放っておける非同期型

OpenAI Codexのクラウド実行は、他の2つとは実行環境そのものが違う。ローカルのターミナルではなく、隔離されたクラウドの サンドボックスでタスクが進み、完了すると結果を確認してPRを開く、という投げて放っておく運用が前提になっている。

並列で動かせるスレッド数は agents.max_concurrent_threads_per_session という設定項目で決まる。 ブログ記事では「最大8並列」のように紹介されているのをよく見かけたが、公式ドキュメントを確認する限りこれは固定値ではなく、 設定で変更できる上限値だった。サブエージェント同士はここでも独立していて、互いに通信せず、結果は最後にまとめて統合される。

モデルは gpt-5.6 系列が使われ、速度を優先した gpt-5.6-terra や、反復作業向けの gpt-5.6-luna といった派生が用意されている。推論の強さ(model_reasoning_effort)も調整できる。 処理速度そのものを表す具体的な数値は、今回参照した公式ドキュメントの範囲では見つけられなかった。

Git worktreeという裏方

3ツールとも、ドキュメントのどこかに「Git worktree」という単語が出てくる。1つの .git を共有しながら、 ブランチごとに別々の作業ディレクトリを用意できるGitの機能で、複数のエージェントが同じリポジトリを同時にいじっても ファイルの取り合いにならないようにする裏方の役回りだ。

ここで注意したいのは、worktreeは各ツールが独自に発明した並列機構ではなく、Gitそのものの一般的な機能だという点だ。 Claude Codeのドキュメントでは、Agent Teamsのような自動調整を使わずに複数セッションを手動で並走させる手段として worktreeが紹介されている。ツールの売りである並列機能と、その下で使われている土台部分は分けて見た方が実態に近い。

見えてきた設計の違い

当初の疑問は「どのツールが一番速いか」だったが、公式ドキュメントを読み比べていくと、それよりも 「エージェントに何を任せたいか」という設計思想の違いの方がはっきり見えてきた。

ワーカー同士が議論しながら進めてほしいなら、今のところ3つの中で唯一その形を持っているのはClaude CodeのAgent Teamsになる。 ただし実験的機能で環境変数を立てる必要があり、トークンも余計に食う。すでにタスクの分け方が決まっていて、それを機械的に 高速化したいだけならGitHub Copilotの /fleet が向いていそうだし、タスクを投げてしばらく他の作業をして、 後からまとめてPRを見返したいならOpenAI Codexのクラウド実行が合っている。日常的にちょっとした調べ物やサブタスクを 1つ切り出したいだけなら、Claude CodeのSubagentsのような軽量な報告型で十分なことも多い。

ネット上の比較記事に出てくる具体的な速度や並列数の数字は、計測条件も情報源もまちまちで、鵜呑みにするのは危ういと感じた。 仕組みそのものを公式ドキュメントで確認してから選ぶ方が、結局は近道になる。
