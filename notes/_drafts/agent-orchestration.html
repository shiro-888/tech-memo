エージェントオーケストレーション入門 — 複数の AI に役割分担させて1つの仕事を仕上げる

AI 2026-07-02

1体の万能な AI にすべてを丸投げするのではなく、役割の違う複数の AI （エージェント）に仕事を分担させ、それらを1つのタスクとしてまとめ上げる—— この考え方をエージェントオーケストレーション（Agent Orchestration）と 呼びます。オーケストラの指揮者が各パートをまとめて1つの曲に仕立てるのになぞらえた言葉です。

このノートは、ソフトウェア開発の基礎はあるけれど、複数の AI を連携させる 「マルチエージェント」の仕組みは初めてという方を対象にしています。読み終える頃には、 なぜ役割分担が有効なのか、どんな組み合わせ方（パターン）があるのか、そして どんな落とし穴に気をつければよいかの全体像がつかめることを目標にします。 LLM やエージェントといった用語はそのつど「用語補足」で説明するので、AI の詳細を知らなくても 読み進められるはずです。おもしろいことに、この記事自身も複数エージェントの分業で 書かれています。その制作フローも後半で実例として紹介します。

エージェントとオーケストレーションとは

まず土台となる言葉を、身近なイメージに置き換えて整理しておきましょう。

  • LLM（大規模言語モデル）：大量の文章から言葉のパターンを学習し、 与えられた指示（プロンプト）に対して自然な文章を返す AI。ChatGPT や Claude の 頭脳にあたる部分です。
  • エージェント：LLM に「道具（ツール）を使う手足」を 付けたもの。文章を返すだけでなく、ファイルを読み書きしたり、コマンドを実行したり、 Web を検索したりと、目標達成のために自分で手順を選んで動く AI を指します。
  • ツール利用（ツールコール）：エージェントが「ファイルを読む」「検索する」 といった外部の道具を呼び出すこと。用語補足：LLM 自体は文章を生成するだけなので、 実際の操作は「この道具をこの引数で使いたい」という要求を出し、その結果を受け取って 次の判断に使います。この繰り返しでエージェントは作業を進めます。
  • サブエージェント：大きな仕事の一部分を担当する、専門特化した子エージェント。 「調査担当」「レビュー担当」のように役割を絞って使います。
  • オーケストレーション（指揮・編成）：複数のエージェントを いつ・どの順で・どう連携させるかを調整し、全体を1つの成果へまとめること。 この調整役を担うエージェントをオーケストレーター（指揮者）と呼びます。

つまりエージェントオーケストレーションとは、「専門の異なる複数のエージェントを、 指揮役がまとめて1つのタスクを完遂させる仕組み」です。人間のチームで、 リーダーが担当者に仕事を割り振り、成果を統合するのとよく似ています。

なぜ役割分担が必要か — 単一エージェントの限界

「1体の賢い AI にぜんぶ任せればいいのでは？」という疑問はもっともです。実際、 単純な作業なら単一エージェントで十分です。しかし仕事が大きく複雑になるほど、 1体に集約する方式には次のような限界が見えてきます。

  • コンテキストの肥大：エージェントが一度に扱える文脈 （コンテキスト＝会話や資料の記憶枠）には上限があります。長い作業を続けると 情報が膨らみ、序盤の指示を取りこぼしたり、注意が散漫になって精度が落ちます。
  • 役割の混在：「作る」「点検する」「まとめる」を1体が兼ねると、 自分の成果を自分で甘く評価しがちです。人間でも、書いた本人より第三者のほうが 誤りに気づきやすいのと同じです。
  • 手順の見通しの悪さ：複数の工程が1つの長い思考に混ざると、 どこで間違えたのか、どこをやり直せばよいのかが追いにくくなります。

単一エージェント vs 複数エージェント

そこで、仕事を工程ごとに切り分け、それぞれ専門のエージェントに任せる方式が有効になります。 両者を対比すると違いがはっきりします。

  • 関心の分離：各エージェントは自分の役割だけに集中できるため、 プロンプト（指示）を専門特化でき、精度が上がりやすい。
  • 独立した検証：作る担当と点検する担当を分ければ、第三者の目で 品質を確認できる。誤りやすい思い込みを別のエージェントが拾える。
  • 見通しと再実行のしやすさ：工程が分かれていると、失敗した工程だけを やり直せる。全体を最初からやり直す必要が減る。
  • 並列化：互いに依存しない工程は同時並行で進められ、時間を短縮できる。

ただし、複数エージェント化は万能薬ではありません。役割の受け渡しや 調整のぶんだけ、設計の手間・実行コスト・待ち時間は増えます（後述の「落とし穴」参照）。 単純な作業はあえて単一エージェントのままにし、複雑さが分担の オーバーヘッドを上回るときに初めて分割する——この見極めが実務では大切です。

代表的な構成パターン

エージェントの組み合わせ方には、いくつかの定番パターンがあります。まずは次の4つを 知っておけば十分です。実際のシステムはこれらを組み合わせて作られます。

  • オーケストレーター／ワーカー型：指揮役（オーケストレーター）が 仕事を分解し、作業役（ワーカー）へ割り振って結果を統合する。 向き：全体の段取りを1か所で管理したいとき。もっとも基本的で応用が利く。
  • シーケンシャル（パイプライン）型：処理を一直線につなぎ、前の出力を 次の入力にして順番に渡す。向き：工程の順序がはっきり決まっている作業 （例：下調べ→執筆→校正）。
  • 並列（ファンアウト／ファンイン）型：1つの仕事を複数に分けて同時に処理し （ファンアウト）、結果を1つに集約する（ファンイン）。向き：独立した 調べ物を手分けするなど、待ち時間を減らしたいとき。
  • レビュー／批評ループ型：生成役と評価役を分け、評価役が合格を出すまで 修正を往復させる。向き：品質が重要で、第三者チェックを効かせたいとき。

用語補足（ファンアウト／ファンイン）：「ファンアウト」は1つの入口から 複数の処理へ枝分かれさせること、「ファンイン」は複数の結果を1つの出口へ束ねることを指す 言い回しです。

次章で紹介するこのノートの制作フローは、「オーケストレーター／ワーカー型」を土台に、 要所で「レビュー／批評ループ型」を組み込んだ構成になっています。パターンは 排他的なものではなく、こうして重ねて使うのが実際的です。

実例：このノートはどう作られているか（5つの役割）

抽象的な話が続いたので、具体例を見てみましょう。この tech-memo の記事は、次の 5つの役割を持つエージェントの分業で作られています。これは特別な話ではなく、 オーケストレーター／ワーカー型とレビューループを組み合わせた、ごく標準的な構成の一例です。

  • orchestrator（統括・司令塔）：利用者の窓口。要望を受け取り、 以下の各役割を適切な順で呼び出し、最終成果をまとめて返す指揮者。
  • issue-manager（課題抽出）：要望を分析して「何を解決すべきか」を 課題として構造化する。曖昧な点は質問として洗い出す。
  • planner（計画立案）：課題を実現するための手順・タスク分割・ 担当割り当てを設計する。
  • reviewer（レビュー）：計画や成果物を独立した視点で点検し、 合否と改善点を返す。品質の番人。
  • reporter（報告）：作業全体の記録を取り、最終的な報告書に整える。

大まかな流れは「課題抽出 → 計画 → 計画のレビュー → 実行 → 成果物のレビュー → 報告」で、 レビューで問題が見つかれば前の工程に差し戻して直します（図1）。ポイントは、 作る役割と点検する役割が分かれていること。だからこそ、自分では気づきにくい 抜けや誤りを別の視点で拾えます。

なお、この5つの役割分担は「この記事を作るときの進め方」を説明したもので、 リポジトリ上で誰でも動かせる形で公開しているのは、/draft（トピックから下書きを 起こして下書き PR を作る）と /publish（下書きを公開する）という2つの スラッシュコマンドです。この記事自身も /draft の流れに沿って 用意されています。

コンテキストの引き継ぎ — オーケストレーションの肝

複数エージェントを連携させるうえで、いちばんの肝はコンテキスト（情報）の 引き継ぎです。というのも、多くの構成でサブエージェントは毎回まっさらな状態で 起動する（コールドスタート）——つまり前の担当者との会話を見ていない からです。人間のチームでも、口頭だけで伝えた内容は抜け落ちます。だからこそ、 受け渡しを形に残す工夫が要ります。

よく使われるのが、中間成果物をファイルに書き出して次の担当へ渡す方法です。 このノートの制作フローでも、各工程が次のようなファイルを残し、次のエージェントは 「このファイルを読んで作業して」と指示されて起動します。

  • 要望の原文（orchestrator が保存）
  • 抽出した課題リスト（issue-manager）
  • 実行計画（planner）
  • レビュー結果（reviewer）
  • 最終報告書（reporter）

さらに、課題・タスク・レビュー指摘にはそれぞれ ISS-001、T-001、 REV-001 のような通し番号（ID）を振ります。こうしておくと、 「計画の T-003 は課題 ISS-005 に対応」「レビュー指摘 REV-002 を直した」のように、 工程をまたいで同じものを正確に指し示せるようになります。会話が見えない 相手同士でも、ファイルと ID を共通の“地図”にすることで、認識のズレを防げるわけです。

注意点・落とし穴

複数エージェント化には見返りがある一方、固有の落とし穴もあります。代表的なものを 「症状 → 対策」の形で挙げます。

  • 指示の取りこぼし（症状）：コールドスタートのため、前提や決定事項が 次の担当に伝わらず、ちぐはぐな成果になる。対策：中間成果物を ファイルに残し、呼び出し時のプロンプトにも要点を再掲する（二重で渡す）。
  • コスト・待ち時間の増加（症状）：エージェントを呼ぶたびに LLM の 利用料と処理時間がかかり、工程が増えるほど積み上がる。対策：分割は 必要な範囲にとどめ、独立した工程は並列化して待ち時間を圧縮する。
  • 差し戻しの無限ループ（症状）：レビューと修正を延々と往復し、 いつまでも終わらない。対策：往復回数の上限を決め、超えたら人間に 判断を仰ぐ、または現状で打ち切るルールを設ける。
  • 役割の分割しすぎ（症状）：細かく割りすぎて受け渡しばかりが増え、 かえって非効率になる。対策：1エージェント＝1つの明確な責務を目安にし、 過剰な細分化を避ける。
  • そもそも過剰設計（症状）：単純な作業に多段構成を持ち込み、 手間だけが増える。対策：まず単一エージェントで試し、 実際に困ってから分担を導入する。

小さく始めるには

エージェントオーケストレーションは、最初から5役割をそろえる必要はありません。むしろ いちばん効果の出やすいところから、少しずつ導入するのが現実的です。

  • まずは「実行役」と「レビュー役」の2つから始める。作ったものを 別のエージェントに点検させるだけで、品質の底上げを体感できる。
  • 次に、繰り返す前処理（要望の整理や課題の洗い出し）を専門役へ切り出す。
  • 独立して進められる調べ物が出てきたら、並列化で待ち時間を縮める。
  • 工程が増えてきたら、全体を束ねるオーケストレーター（指揮役）を立て、 受け渡しをファイル＋ID で明確にする。

呼び出しのイメージは、おおむね次のような擬似コードで捉えられます（具体的な書き方は 利用するフレームワークの公式ドキュメントに従ってください。下記はあくまでイメージです）。 

# 擬似コード（イメージ）：作って→点検して→直す、の最小オーケストレーション
draft  = writer_agent("記事を書いて", context_file="request.md")
review = reviewer_agent("この下書きを点検して", context_file=draft)

while review.rejected and attempts < MAX_ATTEMPTS:   # 無限ループを防ぐ上限
    draft  = writer_agent("指摘を直して", context_file=review)
    review = reviewer_agent("再点検して", context_file=draft)

publish(draft)   # レビューを通過したら次の工程へ

まとめ

エージェントオーケストレーションとは、専門の異なる複数のエージェントを指揮役が まとめ、1つのタスクを完遂させる仕組みです。単一エージェントの限界 （コンテキスト肥大・役割混在・見通しの悪さ）を、関心の分離・独立した検証・ 再実行のしやすさ・並列化で補うのが狙いでした。オーケストレーター／ワーカー型を 土台に、レビュー／批評ループなどを組み合わせて設計します。連携の肝は コールドスタートを前提に、中間成果物のファイルと ID でコンテキストを確実に 引き継ぐこと。一方でコスト増や無限ループ、過剰設計といった落とし穴もあるため、 まず単一で試し、困ってから小さく分担を足していくのが賢明です。 この記事自身がその分業で作られていることが、いちばん身近な実例です。
