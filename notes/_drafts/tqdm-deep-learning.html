tqdmで深層学習の学習ループを可視化する

ツール 2026-08-15

学習を回している間、ターミナルが何十分も黙り込むことがあります。GPUのファンだけが うなっていて、ログは一行も流れてきません。フリーズしているのか、順調に進んでいるのか、 そもそも合っているループを回しているのかすら、画面を眺めているだけでは判断がつかない。 そんな経験に心当たりのある方は多いのではないでしょうか。

この「今どこにいるか分からない」不安を消してくれるのが、Pythonの進捗バーライブラリ tqdmです。名前はアラビア語で「進歩」を意味するtaqaddumに由来し、 スペイン語のte quiero demasiado（あなたをとても愛してる）の略でもあるという、 公式サイトいわく洒落の効いた由来を持っています。深層学習の文脈では、エポックや ミニバッチのループにひとかぶせするだけでETA（残り時間の見積もり）が出る手軽さから、 ほぼ標準装備のように使われています。このノートでは基本の使い方から学習ループへの 組み込み方、ハマりやすい落とし穴まで、実際に動かして確認しながら整理します。

A Fast, Extensible Progress Bar for Python and CLI（tqdm公式リポジトリの説明より）

基本はイテラブルを包むだけ

インストールはpipで一発です。 

pip install tqdm

使い方も単純で、既存のfor文が回すイテラブルをtqdm()で包むだけです。 

from tqdm import tqdm
import time

for i in tqdm(range(10000)):
    time.sleep(0.001)  # ここに学習の1ステップが入る

range(N)をtqdmで包む組み合わせはよく使うので、trange(N)という 短縮形も用意されています。実行すると、次のような1行がターミナルに表示されます （この記事のために実際に動かして確認したものです）。 

train:  45%|##############8                  | 450/1000 [00:12<00:15, 36.29it/s]

この1行に、進捗率・経過時間・残り時間の見積もり・処理速度という、学習を見守るうえで 欲しい情報がほぼ詰め込まれています。手動でprint(f"{i}/{total}")を 書いていた頃を思うと、拍子抜けするくらい省エネです。表示される文字はターミナル次第で 変わり、Unicode対応の端末では塗りつぶしブロックで描かれますが、非対話環境 （このノートの検証環境や、後述するCIのログなど）ではasciiの#にフォールバックします。 見た目が違っても中身の情報は同じなので、慌てる必要はありません。

バー1行が伝えている情報

先ほどの1行を分解すると、次の5つのパーツに分かれます。

学習ループへの組み込み方

深層学習の学習ループでtqdmが力を発揮するのは、PyTorchのDataLoader （学習データを一定件数ずつまとめて取り出す仕組み）をそのまま包んで、バッチごとに lossやaccuracyをバーの右端に流し込めるところです。set_postfix()に 辞書やキーワード引数を渡すと、バーを崩さずに末尾へ追記してくれます。 

from tqdm import tqdm

running_loss = 0.0
pbar = tqdm(train_loader, desc=f"epoch {epoch}")
for step, (x, y) in enumerate(pbar, start=1):
    optimizer.zero_grad()
    out = model(x)
    loss = criterion(out, y)
    loss.backward()
    optimizer.step()

    running_loss += loss.item()
    pbar.set_postfix(loss=f"{running_loss / step:.3f}")

train_loaderがPyTorchのDataLoaderであっても、ただのリストであっても、tqdmから 見れば「長さの分かるイテラブル」でしかありません。だからこの書き方はフレームワークを 問わず使い回せます。なおtqdm側の挙動（set_postfixの表示や更新タイミングなど）は この記事のためにダミーデータで実際に動かして確認済みです。modelやoptimizerの部分は PyTorchの学習ループとしてよく見る定型的な書き方に沿っています。

エポックとバッチを二重に見せる

エポックの外ループとバッチの内ループを両方バーにしたいときは、position 引数で表示行を分けます。内側のバーは1エポックごとに作り直すので、 leave=Falseを付けて役目を終えたら消してやるのがコツです。付け忘れると、 エポックを重ねるたびに使い終わったバーが画面にずらずら積み上がっていきます （実際にやってみて、スクロールが止まらなくなって気づきました）。 

from tqdm import tqdm, trange

for epoch in trange(EPOCHS, desc="epoch"):
    running_loss = 0.0
    pbar = tqdm(train_loader, desc=f"  train[{epoch}]", leave=False)
    for step, (x, y) in enumerate(pbar, start=1):
        loss = train_step(x, y)  # 前節と同じ学習処理（forward/backward/step）をまとめた想定
        running_loss += loss.item()
        pbar.set_postfix(loss=f"{running_loss / step:.3f}")

printを挟むとバーが崩れる

学習ループの途中でチェックポイントの保存やログ出力のためにprint()を 呼ぶと、バーの描画が乱れて画面が崩れます。tqdmはカーソルを同じ行に戻して上書きする 前提で動いているため、そこに割り込んでprintされると行がずれてしまうからです。代わりに tqdm.write()を使うと、バーを一瞬どけてメッセージを流し、また同じ場所に バーを復元してくれます。 

from tqdm import tqdm

for i in tqdm(range(steps)):
    if i == checkpoint_step:
        tqdm.write(f"checkpoint saved at step {i}")

loggingモジュールを使っている場合も注意が必要です。StreamHandlerがそのまま printしてしまうとバーを壊すので、tqdm.write()をハンドラ経由で呼ぶか、 学習中だけログレベルを絞るといった工夫が要ります。

CIやログファイルに流すと様子が変わる

ここが個人的に一番ハマったところです。ターミナルで動かしている分には快適なtqdmも、 標準出力をファイルにリダイレクトしたりCIのログに流したりすると様子が一変します。 tqdmはバーを更新するたびに行の先頭へカーソルを戻す制御文字（キャリッジリターン）を 送っているだけなので、実際のターミナルなら上書きされて1行に見えても、ただの テキストファイルにはその制御文字ごとそのまま溜まっていきます。試しに30ステップの ループをファイルへリダイレクトしてみると、こうなりました。 

$ python train.py > train.log 2>&1
$ wc -c train.log
376 train.log

30ステップしか回していないのに、9回分のバーの状態がキャリッジリターンで区切られた まま1つのファイルにぶら下がっています。ログビューアによってはこれが読みにくい塊として 表示されます。対策は主に2つで、更新頻度そのものを下げるminintervalと、 TTYでないときはバーごと出さないdisableです。 

import sys
from tqdm import tqdm

for i in tqdm(range(steps), disable=not sys.stdout.isatty()):
    pass  # ここに学習の1ステップが入る

sys.stdout.isatty()は、出力先が人間の見ている端末かどうかを教えて くれます。手元のターミナルではTrueになってバーが出ますが、CIやリダイレクト先では Falseになるのでdisableが効き、バーそのものが消えてログはprint()相当のシンプルな 行だけになります。実際に上のコードでリダイレクトを試すと、出力ファイルの中身は 最終行だけの数バイトになりました。

JupyterやColabではimportを変える

ノートブック環境でtqdm.tqdmをそのまま使うと、セルの中に文字列のバーが再描画され 続けて見づらくなります。tqdm.notebookを使うと、ipywidgetsベースの 本物のプログレスバーウィジェットに切り替わります。 

from tqdm.notebook import tqdm, trange

スクリプトとノートブックの両方で同じコードを使い回したいなら、tqdm.auto が環境を見て適切な実装を選んでくれます。 

from tqdm.auto import tqdm

迷ったらとりあえずtqdm.autoにしておく、くらいの感覚で十分です。

複数GPUでは1プロセスだけに絞る

DistributedDataParallel（DDP）などでプロセスを複数並べて学習する場合、全プロセスが それぞれtqdmを表示すると、同じ内容のバーがプロセス数だけ重なって流れてきます。 GPU4枚なら4本、8枚なら8本です。よくあるのは、rank（プロセスの通し番号）が0の プロセスだけでバーを出し、他のプロセスはdisable=Trueにしてしまう 書き方です。 

# 擬似コード（イメージ）。実際のrank取得はフレームワークの流儀に従う
pbar = tqdm(train_loader, disable=(rank != 0))

rankの取り方は分散学習フレームワークによって変わるので、上のコードはあくまで イメージです。実際に組むときは使っているフレームワークの流儀に合わせてください。

最初に覚えておけば十分なこと

機能はいろいろ挙げましたが、日常的に使うのはごく一部です。for文をtqdm()で包むこと、 set_postfix()でlossを流すこと、printの代わりにtqdm.write()を使うこと。この3つを 押さえておけば、たいていの学習ループは困りません。CIのログが荒れて気になったときに disableとmininterval、ノートブックで見づらいと感じたときにtqdm.autoを思い出せれば、 それで十分です。
