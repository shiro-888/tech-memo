Anthropic公式記事に見るAIエージェント構築のベストプラクティス

AI 2026-08-20

この記事は AI エージェントが作成しています。内容に誤りが含まれる場合があるため、重要な情報は公式ドキュメント等の一次情報でご確認ください。

「AIエージェントの作り方」を指南する記事は、もはや数えきれないほどあります。ただ、そのほとんどは 又聞きの二次情報で、辿っていくと結局は同じ元ネタに行き着くことが少なくありません。実はその元ネタの 多くは、Claudeを作っているAnthropic自身が、自社のエンジニアリングブログで丁寧に書いています。 マルチエージェントの研究システムをどう設計したか、ツールの説明文ひとつでどれだけ精度が変わったか、 長時間動き続けるエージェントが何を忘れて何を壊すか。どれも実際に手を動かした上での報告で、 読み応えがあります。

このノートは、そうしたAnthropic公式のエージェント関連記事を一度に見渡せるよう、テーマ別に整理し 直したものです。あくまで見取り図と要点であり、原典の厳密な要約ではありません。気になった項目が あれば、リンク先の本文を直接読むことを前提にしています。

出発点になる2本、エージェントとは何か

最初に読むべきは、この2本です。ここで語られている前提を共有していないと、以降のどの記事も 文脈がつかみにくくなります。

Building Effective AI Agents （2024年12月公開）は、シリーズの起点にあたる記事です。ワークフロー （LLMとツールを事前に決めたコードパスで動かす仕組み）とエージェント （LLM自身がプロセスとツール利用を動的に決める仕組み）をまず区別し、プロンプトチェイニング・ ルーティング・並列化・オーケストレーター/ワーカー・評価者/最適化者という5つの定番パターンを 紹介します。核心にあるのは、複雑さは測定可能な改善が伴うときだけ足すという一貫した姿勢で、 いきなりフレームワークに頼るのではなく、まずシンプルな組み合わせで十分かを疑うことを勧めています。

Best practices for Claude Codeは、 その考え方をコーディングエージェントの実践に落とし込んだガイドです。Claudeに検証手段 （テスト・ビルド・スクリーンショットとの比較など）を与えて自走させること、実装前にplanモードで 探索と計画を分離すること、CLAUDE.mdには書かないとClaudeが間違えることだけを書くこと、 サブエージェントで調査をメインの文脈から切り離すことなど、コンテキストウィンドウの逼迫を前提に した具体的な工夫が並びます。もともとはanthropic.com/engineering/claude-code-best-practices という記事でしたが、現在はClaude Codeの公式ドキュメントへ統合されています。

複数のエージェントに分担させる

1体のエージェントで足りない場面には、複数体制という選択肢があります。 How we built our multi-agent research system （2025年6月公開）は、Anthropicの「Research」機能を支えるマルチエージェント構成の裏側をまとめた 記事です。Opus 4をリードエージェント、Sonnet 4を並列サブエージェントに据えたオーケストレーター/ ワーカー構成で、社内の評価では単一のOpus 4を90.2%上回ったと報告されています。

一方で代償も率直に書かれています。通常のチャットに比べてエージェントは約4倍、マルチエージェント 構成は約15倍のトークンを消費するため、高価値なタスクにしか経済的に見合いません。単純な質問に 50体ものサブエージェントを生成してしまう暴走、毎回異なる判断を下す非決定性ゆえのデバッグの難しさ、 長時間動かすためのチェックポイントや段階的デプロイの必要性など、マルチエージェントならではの 運用課題が具体的な数字つきで語られているのが読みどころです。

エージェントを支える3つの材料

エージェント自体の設計方針が決まったら、次は中身です。Anthropicはツール・コンテキスト・スキルと いう3つの構成要素それぞれに、単独の記事を割いています。

Writing effective tools for AI agents, using AI agents （2025年9月公開）は、エージェント向けのツール設計が従来のAPI設計と何が違うかを整理しています。 既存APIをそのまま薄くラップするのではなく、エージェントのコンテキスト消費量を意識した粒度にする こと（連絡先の全件返却ではなくsearch_contactsのような検索型ツールにする、など）、サービスごとに 名前空間を切ること、エラーメッセージは次に取るべき行動を示唆する文にすることなどが挙げられて います。さらに踏み込んで、Claude自身にツールの評価結果を分析させ、説明文や設計を改善させるという 手法も紹介されており、記事タイトルの「using AI agents」はこの部分を指しています。

Effective context engineering for AI agents （2025年9月公開）は、単発のプロンプトを書く「プロンプトエンジニアリング」と、複数ターンにわたって 蓄積される情報を選別し続ける「コンテキストエンジニアリング」を切り分けた上で、後者の勘所を解説して います。長時間タスクでコンテキストが埋まってきたときの対処として、要約して圧縮するcompaction、 コンテキスト外の永続メモリにメモを取るstructured note-taking、専門特化したサブエージェントに 探索させて要約だけ持ち帰らせるsub-agent構成の3つを、タスクの性質に応じて使い分けるよう勧めて います。

Equipping agents for the real world with Agent Skills （2025年10月公開）は、Claudeが動的に見つけて読み込める「フォルダ形式の手順書」であるAgent Skills の仕組みを紹介しています。SKILL.mdの名前と説明だけを常にシステムプロンプトへ載せておき、 関連しそうな場面で本文を読み込み、さらに必要なら同梱の参照ファイルを読み込むという3段階の 「プログレッシブディスクロージャー」により、使わないスキルの分までコンテキストを圧迫しない 設計になっています。

動かす場所を選ぶ、SDKとホスト型基盤

考え方と材料が揃ったら、実際にどこでエージェントを動かすかという話になります。ここは自分で組む 場合と、Anthropicのホスト型基盤に任せる場合とで記事が分かれています。

Building agents with the Claude Agent SDK （2025年9月公開）は、Claude Codeの内部で使われている土台をSDKとして切り出したものの紹介です。 「エージェントにコンピュータを与える」という発想のもと、コンテキスト収集・アクション実行・ 成果検証・反復改善という4段階のフィードバックループを自分のアプリケーションに組み込めます。 コーディング以外にも、金融分析や旅行手配、カスタマーサポートなど幅広い用途を想定していると 書かれています。

Effective harnesses for long-running agents （2025年11月公開）は、1つのコンテキストウィンドウに収まらないほど長く動くエージェントを、 自前の「ハーネス」（実行環境と管理の仕組み）でどう支えるかという実例です。最初のセッションで 200件を超える要件をJSONの機能リストに書き出し、以降のセッションは1機能ずつ着実に進めては コミットする、という2段階構成が紹介されています。テストを勝手に削除・改変させないよう明示的に 禁止する一文を加えたという工夫は、AIエージェントが完了したことにしてしまう挙動への率直な対処 として印象的です。

Scaling Managed Agents: Decoupling the brain from the hands （2026年4月公開）は、上記のような長時間エージェントをAnthropicがホスト型サービスとして提供する 際の設計を解説しています。頭脳にあたるClaudeと処理ループ、手足にあたるサンドボックスや外部 ツール、セッション記録を1つのコンテナに詰め込むのではなく別々のリソースへ切り離すことで、 サンドボックスが落ちても頭脳側の状態は失われず、認証情報もサンドボックスの外に安全に置ける ようになったといいます。自前でハーネスを組む前段の記事と、ホスト型に任せる際の設計をまとめた この記事は、対になる関係にあります。

ちゃんと機能しているかを測る

Demystifying evals for AI agents （2026年1月公開）は、エージェントの評価が単発のチャット応答の評価よりなぜ難しいかを整理した 記事です。自律性が高く、同じ入力でも毎回違う経路を辿るため、発言内容だけでなく実際に環境が どう変化したか（例えば予約システムに本当に予約が入っているか）まで確認する必要があると説きます。 ツール呼び出しや推論を含む一部始終であるtrajectoryと、試行終了時点の状態である outcomeを区別すること、コードベース・モデルベース・人手という3種類の採点方法を 使い分けること、非決定性に対応するためpass@k（k回中1回でも成功）とpass^k（k回とも成功）の両方で 見ることなど、評価設計の実務的な原則が並びます。

土台にあるプロトコル、MCP

ここまでの記事の随所で前提になっているのが、Model Context Protocol（MCP）です。 Introducing the Model Context Protocol （2024年11月公開）は、AIアシスタントを外部のデータソースやツールに接続するための、Anthropicが 提案したオープンな標準規格です。データを提供する側のMCPサーバーと、AIアプリケーション側の MCPクライアントという2層構造で、接続先ごとに個別実装が必要だった状態を単一のプロトコルに 置き換えることを狙っています。

Donating the Model Context Protocol and establishing the Agentic AI Foundation （2025年12月公開）では、AnthropicがMCPをLinux Foundation傘下の新設団体Agentic AI Foundationへ 寄贈したことが発表されています。共同創設者にはBlockやOpenAIも名を連ね、Blockのgoose、OpenAIの AGENTS.mdと並ぶファウンディングプロジェクトという位置づけです。公開から1年ほどで1万を超える MCPサーバーが稼働しているという実績を背景に、特定企業に依存しない中立な標準として運営を続けて いく意思表示だと言えます。

読む順番に迷ったら

情報量が多いので、目的別に入り口を絞ると読みやすくなります。初めてエージェントを設計するなら Building Effective AI AgentsとClaude Codeのベストプラクティスの2本で十分に土台ができます。 ツールやプロンプトの精度で悩んでいるならWriting effective tools for AI agentsとEffective context engineeringが直接効きます。本番投入や長時間運用が課題ならEffective harnessesとScaling Managed Agentsを、複数エージェントの構成に興味があればマルチエージェント研究システムの記事を読むのが 早道です。全部を一度に読む必要はありません。
