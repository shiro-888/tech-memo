内製開発を検討するときの RASCI フレームワーク — 「誰が何に責任を持つか」を1枚の表で決める

設計 2026-07-16

システム開発を外部のベンダーに任せる外注（アウトソーシング）から、 自社の人員で作る内製（インソーシング）へ切り替える——。近年よく検討される この選択には、技術面だけでなく「誰が何に責任を持つのか」を組織として決め直す という、見落とされがちな宿題がついてきます。外注では契約書とベンダーが引き受けてくれていた 判断や責任が、内製にした途端に自分たちの側へ移ってくるからです。

この「役割と責任のあいまいさ」を、たった1枚の表で解きほぐす道具が RASCI（ラスキ）フレームワークです。このノートは、 プロジェクト管理の手法にはあまり触れてこなかったエンジニアを対象に、 RASCI とは何か、どう表を作るのか、そして内製開発を検討・推進する場面でどう効くのかを、 用語をそのつど補足しながら解説します。読み終える頃には、自分のチームの一場面を RASCI の表に落とし込めるようになることを目標にします。

RASCI とは — RACI に「S（支援）」を足したもの

RASCI は、あるタスクや成果物について関係者それぞれがどんな責任を負うかを、 役割の頭文字で書き分けるための枠組みです。もとになっているのは、より広く使われている RACI（レイシー）という4役割のモデルで、そこに S（Support＝支援） を加えたものが RASCI です。5つの役割は次の意味を持ちます。

  • R — Responsible（実行責任者）：実際に手を動かして作業を進める人。 1つのタスクに複数いてもかまいません。「作る人」です。
  • A — Accountable（説明責任者）：その成果の最終的な責任を負い、 可否を判断・承認するただ1人。R に作業を任せ、完了を見届けます。 用語補足：Responsible が「手を動かす責任」なのに対し、Accountable は 「うまくいったか／いかなかったかを引き受ける責任」です。日本語ではどちらも「責任」なので 混同しがちですが、英語では別の言葉で、役割もはっきり異なります。
  • S — Support（支援者）：R が作業を完遂できるよう、 リソース・専門知識・人手を提供して手伝う人。C（相談先）が「意見を言う」 立場なのに対し、S は実作業に手を貸す点が違います。RACI にはこの役割がなく、 RASCI で明示的に足された部分です。
  • C — Consulted（相談先）：作業や意思決定の前に意見を求める相手。 双方向のやり取り（相談）が発生します。
  • I — Informed（報告先）：物事が決まった後・進んだ後に 結果を知らされる相手。基本は一方向の共有で、相談はしません。

図1は、この5つの役割の関係を1つのタスクを中心に整理したものです。A が全体の責任を持ちながら R に作業を委ね、R を S が手伝い、C には事前に相談し、I には結果を伝える——という向きを表しています。

マトリクス（RASCI 表）の作り方

RASCI は表（マトリクス）で表現します。作り方はシンプルで、次の手順です。

  1. 縦軸にタスク・成果物を並べる：プロジェクトの主な作業や意思決定を1行ずつ書き出します （例：「要件定義」「アーキテクチャ選定」「実装」「リリース判断」）。
  2. 横軸に人・役職を並べる：関わる担当者や役割を1列ずつ置きます （個人名でも「開発リード」「PdM」のような役職でも可）。
  3. 交点に R / A / S / C / I を書き込む：各タスクについて、各人がどの責任を負うかを 1文字で埋めます。担当しないセルは空欄にします。

埋めるときに守るべき基本ルールがあります。とくに最初の2つは重要です。

  • 各行の A（説明責任者）はちょうど1人：これは 「1人のボス」原則と呼ばれます。A が0人だと責任者不在で決めごとが宙に浮き、 2人以上だと責任のなすり合いが起きます。RASCI 表を作る最大の効用は、この 「各タスクの最終責任者を1人に確定させる」ことにあります。
  • 各行に R は最低1人：手を動かす人がいなければタスクは進みません。
  • C と I は0人でも複数でもよい：相談先・報告先は必要に応じて置きます。
  • 1人が同じタスクで A 兼 R を持つのは可：小さなチームでは「自分で決めて自分で作る」 こともあります。ただし C や I まで一人で兼ねると、チェック機能が働かない点に注意します。

内製開発の一場面を RASCI で書いてみる

具体例として、「これまで外注していた社内向けツールを、内製に切り替えるか検討し、 実際に作る」という架空のプロジェクトを RASCI 表にしてみます（表1）。登場する役割は、 事業側の意思決定者（プロダクトオーナー）、開発をまとめる開発リード、実装するエンジニア、 品質を見る QA、そして情報システム部門とします。

オーナー		 開発リード エンジニア QA 情報システム部

要件定義 A R S C I
アーキテクチャ選定 I A R C C
実装 A R S
リリース判断 A R C C I
運用・保守の引き継ぎ I C R I A

  • A 説明責任者

表1: 内製化を検討・実行する架空プロジェクトの RASCI 表。各行の A はちょうど1つになっている。

この表を眺めると、言葉で議論していたときには見えなかったことが浮かび上がります。たとえば：

  • 「内製 / 外注の方針判断」の A はプロダクトオーナー——技術的な相談（C）は 開発リードや情シスに求めつつ、最終判断は事業側が1人で引き受けると明確になります。 ここがあいまいだと「開発が勝手に内製と決めた」「事業が現場を無視した」という対立が起きがちです。
  • 「アーキテクチャ選定」の A は開発リード——技術判断は技術の責任者に委ねる、という 役割分担が表れています。プロダクトオーナーは I（結果を知る）にとどまります。
  • 「運用・保守の引き継ぎ」の A は情報システム部——作って終わりにせず、 内製後に誰が面倒を見るのかを先に決めておく。内製化でとくに抜けやすい論点です。

なぜ内製開発の検討で RASCI が効くのか

RASCI 自体はあらゆるプロジェクトで使える汎用ツールですが、内製開発の検討という 場面ではとりわけ相性がよい理由があります。

  • 外注時に「外」にあった責任が「内」に移る：外注では、品質・納期・保守の責任の 多くをベンダーが契約で引き受けていました。内製に切り替えると、その責任が自社の各所へ 再配分されます。誰がどれを引き取るのかを可視化しないと、責任の空白地帯が生まれます。 RASCI はまさにこの再配分を1枚で表せます。
  • 事業側と開発側の境界を引ける：内製では事業部門とエンジニアが密に協働するぶん、 「これは誰が決めるのか」が曖昧になりがちです。A を1人に定める RASCI は、 意思決定の境界線をはっきりさせます。
  • 「支援（S）」を明示できる：内製の立ち上げ期は、専任の担当者だけでは手が回らず、 他チームの一時的な支援に頼ることがよくあります。RACI では表しにくかった 「手伝う人」を、RASCI は S として書けます。誰に・どの程度の助力を 見込んでいるかを事前に共有でき、「頼んだつもり／聞いてない」の齟齬を減らせます。
  • 属人化のリスクが見える：表を作ると、特定の1人に R も A も C も集中している行が 目に見えます。これは内製でありがちな属人化の兆候で、早めに手を打つ材料になります。
RASCI 表の価値は、埋めた結果そのものより、埋める過程で交わす「これは誰の責任？」 という会話にあります。表は合意を記録する器です。

よくある落とし穴

便利な一方で、RASCI にも使い方を誤るとかえって混乱を招く落とし穴があります。 「症状 → 対策」で整理します。

  • A が複数、または不在（症状）：最終責任者があいまいで、決めごとが進まない／ もめる。対策：各行の A はちょうど1人、を最優先ルールとして機械的に点検する。
  • R と A の混同（症状）：「作る人」と「責任を負う人」を区別せず、 全員に R を振ってしまう。対策：「手を動かすのは誰（R）」「うまくいったかを 引き受けるのは誰（A）」を別々に問う。
  • C（相談先）を置きすぎる（症状）：相談先が多すぎて、意見の集約に時間がかかり 意思決定が遅くなる。対策：C は「その意見がないと判断を誤る人」に絞る。 単に知らせたいだけなら I にする。
  • 作って終わりで更新しない（症状）：初期に作った表が実態と乖離し、形骸化する。 対策：フェーズの節目（検討 → 開発 → 運用）で見直す。役割は段階で変わる前提を持つ。
  • 表を作ること自体が目的化（症状）：精緻な表づくりに時間を使い、肝心の合意形成が おろそかになる。対策：粒度は粗くてよい。主要タスク5〜10行から始め、 会話のきっかけとして使う。

小さく始めるには

最初から全タスクを網羅した完璧な表を目指す必要はありません。内製を検討し始めた段階なら、 次のように小さく始めるのが現実的です。

  • まず「内製 / 外注の方針判断」の1行だけを書き、その A（最終責任者）を チームで合意する。ここが決まらないと、その先の議論は空中戦になります。
  • 内製に進めると決めたら、主要な5〜10タスク（要件定義・設計・実装・ リリース判断・運用引き継ぎなど）に広げる。
  • 各行の A が1人になっているかだけ、まず最初に点検する。R・S・C・I の 精度はあとから上げれば十分です。
  • フェーズが変わったら表を見直す。とくに運用・保守の担い手は、 内製化で抜けやすいので早めに埋めておきます。

まとめ

RASCI は、RACI の4役割（R 実行責任者・A 説明責任者・C 相談先・I 報告先）に S 支援者を加えた、責任分担を1枚の表で可視化するフレームワークです。最大のねらいは 各タスクの最終責任者（A）を1人に確定させることにあります。 外注から内製へ舵を切るときは、これまで社外にあった責任が社内へ再配分されるため、 誰がどの責任を引き取るのかがあいまいになりがちです。RASCI 表を使えば、 方針判断・設計・実装・リリース・運用引き継ぎといった各場面の責任の所在を、 事業側と開発側をまたいで見える化できます。完璧な表より、「これは誰の責任？」を 問う会話そのものに価値がある——まずは方針判断の1行と、その A を1人に決めるところから 始めてみてください。
